# ADR 0011: every real TaskRunner call site was missing the poll loop its own contract requires

## What was found, and why it was wrong

`workers/task_runner.py`'s own module docstring has stated, since Phase 9, that "callers poll `get_status()` / fetch `get_result()` once status is COMPLETED" - `InProcessTaskRunner.dispatch()` happens to return an already-terminal handle today, but every call site was always meant to be written against the general async handle-based contract, not against that one implementation's incidental synchronicity.

In practice, none of the six services that dispatch pipeline stages (`audio_service.py`, `emotion_service.py`, `nlp_service.py`, `incongruence_service.py`, `knowledge_service.py`, `retrieval_service.py` - twelve call sites in total) ever actually polled. Each one called `get_status()` exactly once, immediately after `dispatch()`, then proceeded to `get_result()` as though that single check were sufficient. Under `InProcessTaskRunner` this is silently correct, because `dispatch()` already ran the stage synchronously in the caller's own event loop before returning. Under `CeleryTaskRunner`, `dispatch()` only persists a `pipeline_runs` row and enqueues a task - it returns as soon as the message is on the broker, before any real worker has had a chance to pick it up, let alone finish. The single `get_status()` check that followed was therefore checking a `PENDING` (or, if very unlucky in timing, `RUNNING`) row almost every time, and the immediately-following `get_result()` call raised `ValueError: Job <id> has no completed result` - a hard failure, not a fallback - even though the same job went on to complete successfully a few hundred milliseconds to several seconds later.

This was never caught by the existing test suite because every CI run and every local dev default uses `TASK_RUNNER=in_process` (see `.env.example`), and the dedicated Celery tests in `tests/integration/test_celery_task_runner.py` deliberately exercise `CeleryTaskRunner`'s own contract and the worker task body directly (with their own, test-local `_poll_until_terminal` helper) rather than driving a real HTTP request through the actual service call sites end to end with `TASK_RUNNER=celery`. It was found during the final full-pipeline production-readiness validation pass, by doing exactly that: running a real `uvicorn` process with `TASK_RUNNER=celery` against a real worker subprocess and a real HTTP client, which is the one scenario none of the automated tests had previously reproduced.

## The fix

Added `wait_for_completion(task_runner, job_id, *, timeout_seconds=300.0, poll_interval_seconds=0.2)` to `workers/task_runner.py` - a small polling loop that calls `get_status()` repeatedly until the job reaches `COMPLETED`/`FAILED` or a bounded deadline expires (defaulting to `CELERY_TASK_TIME_LIMIT_SECONDS`'s own default, since a real Celery task that hasn't reached a terminal DB state by then has already been killed by its own hard time limit). All twelve call sites across the six services now call this instead of a single `get_status()` check. `InProcessTaskRunner` callers pay no cost: the first status check is already terminal, so the loop exits immediately on its first iteration, exactly as before.

## Why this is the right level of fix

This is a bug fix inside the exact contract the `TaskRunner` Protocol already documented, not a redesign of it - the Protocol's three methods (`dispatch`/`get_status`/`get_result`) are completely unchanged, and `InProcessTaskRunner`/`CeleryTaskRunner` themselves needed no changes either. Only the callers, which had never actually implemented the polling their own architecture called for, were touched.

## Verification

Reproduced live before fixing: a real `uvicorn` server with `TASK_RUNNER=celery`, a real `celery worker` subprocess connected to a real local Redis broker, and a real HTTP request through `POST /conversations/{id}/audio/{asset_id}/process` returned `500 internal_error` with `ValueError: Job <id> has no completed result` in the server log, while the worker's own log showed the same job completing successfully moments earlier. After the fix, the identical request sequence (new conversation, new upload, same endpoint) against the same live Celery worker returned `200`/`201` with `status="completed"` and the correct real transcript, and a follow-up real emotion-inference request through the same Celery path returned a genuine `emotion2vec-tess-emodb-v1` prediction (`model_version_id=782cdb82-342a-422e-8d0f-0c1ee6d73154`) with real confidence/probabilities - both proven work, not assumed from the code change alone. The full backend regression suite and the dedicated real-broker Celery integration tests (`pytest -m requires_redis`) were re-run afterward and remained clean.
