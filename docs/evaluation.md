# Evaluation (Phase 7)

Formal, versioned, non-fabricated evaluation of five real pipelines: speech-to-text (STT), the emotion classifier, retrieval, grounding, and system-level latency/reliability. Every number in this document was produced by actually running one of the `ml/evaluation/evaluate_*.py` scripts below against real data on the date shown - nothing here is invented, estimated, or a target.

## The four states every metric is in

This subsystem exists specifically to never blur these together:

1. **Implemented** - the metric-calculation code exists (e.g. `ml/evaluation/wer.py`).
2. **Executable** - a real evaluation script/dataset/configuration exists that can produce the metric (e.g. `ml/evaluation/evaluate_stt.py` + `stt_datasets/stt_eval_v1.json`).
3. **Actually evaluated** - the script has genuinely been run, and its real output is persisted in an `evaluation_runs` row.
4. **Unavailable** - a required prerequisite (ground-truth labels, a dataset, credentials, an entailment model) does not exist, so the metric is honestly reported as unavailable rather than approximated or faked.

Code existing is never presented as a metric having been evaluated. The dashboard (`GET /evaluations/dashboard`) shows `status="never_run"` with `latest=null` for any evaluation type that hasn't actually been executed yet in a given environment.

## `EvaluationRun`: the shared persistence mechanism

One table (`evaluation_runs`, `models/evaluation_run.py`), insert-only - a new run is always a new row; nothing is ever overwritten, so historical results remain inspectable after a newer run of the same type exists. Every row records: `evaluation_type`, `dataset_version`, `model_version`, `configuration` (exact parameters used), `code_version`, `random_seed` (where applicable), `sample_count`, `status` (`completed`/`partial`/`failed`/`unavailable`), `metrics`, `errors` (per-sample skip/failure records), `notes`, and timestamps. `started_at`/`created_at` use a Python-side (not Postgres server-side) default specifically so that two runs created in the same transaction get genuinely distinct timestamps - see the note in `models/evaluation_run.py` and the regression test in `tests/integration/test_evaluation_dashboard.py` that caught this ordering bug during Phase 7 development.

`GET /evaluations/dashboard` returns the latest run per type; `GET /evaluations/runs?evaluation_type=...` returns full history for comparison. Both endpoints require authentication but are not user-scoped - an evaluation run measures a shared pipeline/model, not private per-user data (same reasoning as `GET /models/{component}`).

## STT evaluation

**Dataset**: `ml/evaluation/stt_datasets/stt_eval_v1.json`, 5 samples. Every `reference_text` was fixed strictly before and independently of any faster-whisper run - Whisper never generated or influenced any reference. See the provenance disclosure below for the more specific question of *who* authored each reference, which is not uniform across the 5 samples:

- `hello_world_fixture` reuses the existing `apps/api/tests/fixtures/hello_world.wav`, synthesized via macOS `say` (a different, non-neural engine than the app's own TTS) - see `apps/api/tests/fixtures/README.md`.
- Four `synthesize_at_eval_time` samples are sentences synthesized fresh at evaluation time via the real Phase 5 `LocalHfTtsProvider` (`facebook/mms-tts-eng`) with a fixed `torch.manual_seed(42)` for reproducibility. This is genuine synthetic-speech audio, not human-recorded speech - a deliberate, documented limitation (no external human-speech corpus is bundled with this repo) rather than a hidden one.

**Honest provenance disclosure - two distinct kinds of "reference," not one**: only `hello_world_fixture`'s reference text ("The quick brown fox jumps over the lazy dog") is independent ground truth in the strong sense - a pre-existing, well-known pangram, fixed in Phase 2 (see `apps/api/tests/fixtures/README.md`), entirely before and independent of both Whisper and this evaluation. The four `synth_0N` reference sentences were **authored by the AI assistant that built this dataset**, in the same working session that created this evaluation - they are original text, and they were never generated by or derived from Whisper (satisfying the strict requirement that references not come from the model under test), but they are **not independent human-sourced ground truth**. No external human author or pre-existing corpus was involved in producing them. This is a real limitation of the current dataset, not a hidden one: of the 5 STT samples, only 1 carries a defensible claim to independent ground truth; the other 4 rest on trusting that a plain declarative sentence was transcribed correctly into text before any audio existed, which is a weaker (though non-circular and reproducible) methodology than a genuine independent-human-transcript corpus such as LibriSpeech. The WER/CER numbers below are computed correctly against these references as they stand; this note does not change them, only what confidence should be placed in the `synth_0N` portion of the result.

**Metrics**: real Levenshtein-based word error rate (WER) and character error rate (CER) - `ml/evaluation/wer.py`, both reference and hypothesis normalized (lowercased, punctuation stripped) before comparison. Latency is `time.monotonic()` measured around the real `FasterWhisperProvider.transcribe()` call only.

**Command**:
```bash
export JWT_SECRET_KEY="$(openssl rand -hex 32)"  # apps/api/.env isn't discovered from repo root
export $(grep -v '^#' apps/api/.env | xargs)      # or just source the real .env values
apps/api/.venv/bin/python -m ml.evaluation.evaluate_stt \
  --dataset ml/evaluation/stt_datasets/stt_eval_v1.json
```

**Actually evaluated, 2026-09-06** (`faster-whisper:tiny`, CPU): n=5, avg_wer=**0.0500**, avg_cer=**0.0363**, avg_latency_ms=**524.6**. Two of the four synthesized samples produced genuine, non-zero errors ("Please schedule" → "Please, kill"; "Machine learning" → "Matching learning") - real TTS pronunciation artifacts the real Whisper model mis-transcribed, not a suspiciously perfect score.

## Retrieval evaluation

**IMPORTANT**: Recall@K/Precision@K/MRR/nDCG require genuine ground-truth relevance judgments - "the chunk the system returned" is never treated as automatically relevant here.

**Dataset**: `ml/evaluation/retrieval_datasets/retrieval_eval_v1.json` + `docs/*.md`. Four short documents (photosynthesis, TCP/IP, the French Revolution, sorting algorithms) were authored specifically for this evaluation - not copied from an external corpus and not generated by the pipeline under test. The real production chunker (`services/knowledge/chunking.py`) was then actually run over them, and relevance judgments for 6 hand-authored queries were assigned by reading the real resulting chunk content - a genuine, if small, human-labeled test collection, not a fabricated one. This is explicitly a small illustrative set (4 documents, 5 chunks, 6 queries), not a claim of production-scale statistical significance.

**What it evaluates**: the real pipeline end to end - `evaluate_retrieval.py` creates a dedicated evaluation conversation, ingests the fixture documents through the real `KnowledgeService` (real parsing/chunking/embedding), and runs the real `RetrievalService.retrieve()` (real pgvector search + real lexical search + real RRF fusion + real cross-encoder reranking) for every query - the exact same code path `/ask` uses.

**Command**:
```bash
apps/api/.venv/bin/python -m ml.evaluation.evaluate_retrieval \
  --dataset ml/evaluation/retrieval_datasets/retrieval_eval_v1.json --k 1 3 5
```

**Actually evaluated, 2026-09-06**: n_queries=6, mrr=**1.0000**; recall@1/3/5=**1.0/1.0/1.0**, precision@1/3/5=**1.0/0.33/0.20**, ndcg@1/3/5=**1.0/1.0/1.0**. A perfect score is expected and honest for this small, topically-distinct 5-chunk corpus (each query has exactly one unambiguous relevant chunk on an unrelated topic) - it demonstrates the real pipeline and metric computation work correctly, not that production-scale retrieval is perfect. See the dataset file's own `description` field for the full methodology note.

## Grounding evaluation

Two metrics are genuinely measurable from data the application already computes at generation time (`services/llm/grounding.py::validate_citations`, called by `rag_service.py` for every real attempt, never self-reported by the model):

- **citation_validity_rate**: of every citation an LLM actually returned, what fraction pointed to a chunk_id genuinely part of that query's retrieved set.
- **grounding_status_distribution**: the real distribution of `grounded`/`partially_grounded`/`ungrounded`/`unavailable` across every real attempt.

`citation_validity_rate` and what the Phase 7 spec calls "retrieval-source alignment" are, in this codebase, the exact same underlying check - see `evaluate_grounding.py`'s docstring for why this is reported as one metric rather than a fabricated second number computed a different-sounding way.

**unsupported_answer_rate is marked UNAVAILABLE**: measuring whether an answer's actual *content* - not just its citation IDs - is supported by the cited text requires an entailment/NLI model or human judgment, neither of which exists in this codebase. It is not approximated by citation-ID validity.

**Command**: `apps/api/.venv/bin/python -m ml.evaluation.evaluate_grounding`

**Actually evaluated, 2026-09-06**: n_generations=3 (every real attempt in this dev environment so far), grounding_status_distribution={grounded: 1, ungrounded: 2}, citation_validity_rate=**1.0** (1/1 citations, 1 generation with citations), unsupported_answer_rate=**UNAVAILABLE**.

## System evaluation

Two real pipelines have well-defined, distinct execution outcomes and are evaluated separately rather than merged into one ambiguous "success" count - see `evaluate_system.py`'s docstring for the exact definitions used:

- **Voice turn pipeline** (`voice_turns.status`): completed/partial/failed/interrupted, with `pending` (still in flight or a stale process) excluded from the completion-rate denominator entirely - it isn't a resolved outcome. Latency percentiles use only `stage_latencies_ms.total_ms` from genuinely `completed` turns.
- **LLM generation attempts** (`llm_generations`): a real success (`model_name` set, no `error_message`), a real failure (`model_name` set, `error_message` present), and an unavailable-provider call (`model_name IS NULL`, no LLM configured at all) are three distinct states. Unavailable-provider calls are never counted as successes, and are excluded from the failure-rate denominator (they were never an attempt).

**Command**: `apps/api/.venv/bin/python -m ml.evaluation.evaluate_system`

**Actually evaluated, 2026-09-06** (this dev environment's accumulated real activity): voice_turns n=12, status_distribution={partial: 5, completed: 1, pending: 4, interrupted: 2}, completion_rate=**0.125** (1 completed / 8 resolved), total_latency p50=p95=**10945ms** (n=1 completed turn with recorded `total_ms`); llm_generations n_real_attempts=3, n_unavailable_provider=8, failure_rate=**0.0**, success_latency p50=p95=**0ms** (n=3 real successes - fast mock-provider calls in this environment, genuinely measured, not fabricated zeros).

These small sample counts are an honest reflection of a lightly-used development environment, not a production SLA claim - re-running these commands after more real usage will produce different, still-real numbers.

## Testing

`tests/ml/test_wer.py` and `tests/ml/test_retrieval_metrics.py` are unit tests of the edit-distance/IR-metric math against known, deterministic fixtures (e.g. "brown"→"black" is exactly one substitution in four words) - these are not real-world evaluation results, and the tests say so explicitly. `apps/api/tests/integration/test_evaluation_dashboard.py` covers the never-run empty state, a real persisted run showing up as evaluated, and - the one genuine bug this phase's testing caught - that two runs created in the same transaction/commit are never ambiguously ordered (see the `EvaluationRun.created_at` fix above).
