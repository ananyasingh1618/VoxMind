# NLP and semantic-vocal incongruence (Phase 4)

## NLP annotation

`NlpService`/`RealNlpAnalyzer` (`services/nlp_service.py`, `services/nlp/analyzer.py`) produce one `NlpAnnotation` per message, combining two genuinely different kinds of components - documented explicitly so neither is mistaken for the other:

| Field | Method | Real or deterministic? |
|---|---|---|
| `sentiment_label`/`sentiment_score` | `cardiffnlp/twitter-roberta-base-sentiment-latest` via a Hugging Face Transformers pipeline (3-class: negative/neutral/positive) | Real neural model, not gated, freely downloadable |
| `entities` | `dslim/bert-base-NER` via a Hugging Face Transformers pipeline (`aggregation_strategy="simple"` merges BIO sub-word tags into whole-entity spans) | Real neural model, not gated |
| `intent_label`/`intent_confidence` | `services/nlp/intent_classifier.py` - fixed regex rules (greeting/gratitude/command/question/statement fallback), checked in priority order | Deterministic rule-based classifier - genuinely computed every time, but explicitly not a trained model; `intent_confidence` is a two-tier scheme (1.0 for a rule match, 0.5 for the fallback), never an invented decimal presented as a calibrated probability |
| `topics` | `services/nlp/topic_extractor.py` - stopword-filtered word-frequency extraction, ties broken by first-appearance order | Deterministic keyword extraction - explicitly not neural topic modeling (no LDA/BERTopic), documented as such so `topics` is never mistaken for a semantic model's output |

`model_versions` on every row records exactly which model/method produced each field (e.g. `{"sentiment": "cardiffnlp/twitter-roberta-base-sentiment-latest", "intent": "rule-based-v1", "topics": "keyword-frequency-v1"}`).

API: `POST /conversations/{id}/messages/{message_id}/nlp/process`, `GET .../nlp`.

## Semantic-vocal incongruence signal

**Naming and framing are deliberate and approved** (see [DECISIONS/0003](DECISIONS/0003-incongruence-not-deception.md)): this is an analytical signal describing divergence between what was said (semantic) and how it was said (vocal) - e.g. flat/incongruent delivery of positive words can indicate sarcasm, stress, or suppressed emotion. It is explicitly **not** a lie detector, deception detector, or truthfulness predictor, and is never named, scored, or described as one anywhere in the codebase, API, or UI. `signal_category: "analytical_not_diagnostic"` is a machine-readable, database-`CHECK`-constrained guardrail against that framing drifting back under later implementation pressure.

`IncongruenceService` (`services/incongruence_service.py`) computes one signal per aligned (speaker-attributed) turn - not per whole message, since a message can contain multiple speaker turns:

1. **Semantic signal**: real sentiment analysis (the same `HuggingFaceSentimentProvider` used for `NlpAnnotation`) run specifically on that turn's own transcript text (`AlignedTurn.text`), not the whole message's text - each turn gets its own semantic reading.
2. **Vocal signal**: that turn's real `EmotionPrediction` (Phase 3 - requires a trained, active emotion model; a turn with no prediction yet is skipped, never fabricated).
3. **Combination** (`services/incongruence/analyzer.py`, `services/incongruence/valence.py`): both signals are mapped onto the same fixed, documented -1.0..+1.0 valence scale (sentiment: positive/neutral/negative → ±1/0; emotion: happy=+1.0, calm=+0.5, neutral/surprised=0.0, sad/angry/fearful/disgust=-1.0 - `surprised` is deliberately neutral since it's an arousal signal with ambiguous polarity). `incongruence_score = |semantic_valence − vocal_valence| / 2.0`, normalized to 0.0-1.0. `confidence` is the *minimum* of the two upstream signals' own confidence - the measurement is only as trustworthy as its weaker input. This step performs no inference of its own; it only compares two already-real signals, so there is nothing here that could fabricate a result.
4. `explanation` is a template string that always states plainly that the signal is analytical only and does not indicate deception - not a claim generated by an LLM.

API: `POST /conversations/{id}/messages/{message_id}/incongruence/analyze`, `GET .../incongruence`.

## What has been genuinely verified

Real end-to-end tests (`tests/integration/test_nlp_pipeline_real.py`, `tests/integration/test_incongruence_pipeline_real.py`, marked `real_model`) exercise the full chain against a real Postgres database: real audio upload → real Whisper transcription/alignment → a registered emotion model → real per-turn emotion predictions → real per-turn sentiment analysis → a genuinely computed incongruence signal, through the live HTTP API. Sentiment/NER models were also verified live through a running server (see `docs/rag.md`'s verification section for the equivalent RAG flow).
